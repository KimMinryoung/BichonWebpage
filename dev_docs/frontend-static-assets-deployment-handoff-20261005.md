# CSS 독립 배포 구조 개선 인수인계

작성: 2026-10-05. 상태: 조사·인수인계만 완료, 구조 개선은 미구현. 다음 세션에서 이 문서와 [운영 참고](frontend-operations.md), [AGENTS.md](../AGENTS.md)를 읽고 현재 코드·운영 상태를 재확인한다.

## 사용자가 요청한 목표

단순 CSS 수정에 전체 테스트, Docker 이미지 빌드, 운영 컨테이너 교체가 매번 필요한 구조를 개선한다. CSS 자체에 Docker 재빌드가 필요한 것은 아니다. 개발 미리보기 사용법 안내만으로 이 요구가 해결되지 않는다.

첫 단계는 CSS만 독립적으로 검증·게시·롤백할 수 있게 하는 것이다. 서버 코드·EJS·의존성 변경은 기존 전체 배포 경로를 유지한다. JS 독립 배포는 앱 버전과의 호환성을 검토한 뒤 범위를 정한다. 초기 구조 도입에는 정상적인 앱 배포가 한 번 필요할 수 있다.

## 확인한 현재 구조

| 위치 | 현행 동작과 개선 시 확인점 |
| --- | --- |
| `Dockerfile` | `COPY . .`로 `public/`을 이미지에 포함하고 `GIT_SHA`를 설정한다. |
| `scripts/deploy` | 전체 검사 → 이미지 빌드 → standby 검증 → 주 컨테이너 교체. 현재 호스트 마운트는 `/app/data`이고 `public/`은 이미지 안에 있다. |
| `config/static-assets.js` | Express가 `public/`을 제공한다. 운영 CSS/JS는 `max-age=31536000, immutable`. 개발은 no-store. 노노그램 HTML·퍼즐 JSON 등 예외가 있다. |
| `config/env.js` | `ASSET_VERSION`은 환경변수 → `GIT_SHA` → 부팅 시각 순서로 프로세스 시작 때 결정된다. |
| `middleware/view-locals.js`, `views/partials/head.ejs` | 템플릿에 `assetVersion`을 전달하고 CSS URL에 `?v=...`를 붙인다. 다른 템플릿·스크립트의 에셋 참조도 조사해야 한다. |
| `middleware/cache-policy.js` | 공개 HTML의 엣지 정책은 `max-age=60, stale-while-revalidate=300`. 새 HTML 참조가 모든 방문자에게 즉시 전달된다고 가정하면 안 된다. |
| `nginx/leninbot-frontend.conf` | 저장소 설정은 Express upstream으로 프록시하며 별도 정적 파일 배포 경로가 없다. 실제 `/etc/nginx` 설정과 일치하는지는 구현 때 확인한다. |
| `scripts/dev-preview` | `public/`, `views/` 등을 바인드 마운트하므로 개발 CSS 수정마다 이미지 빌드할 필요가 없다. 운영 구조와는 다르다. 사용 후 끈다. |

CSS 생성과 Docker 빌드는 구분한다. `public/css/commulingo.css` 수정 후 `node scripts/build-commulingo-list-css.js`로 파생 CSS를 생성한다. `style.css` 계열은 `scripts/build-site-css.js`를 확인한다. 독립 배포에서도 필요한 생성 과정은 유지한다.

## 권장 설계 초안 — 구현 전에 구체화할 것

1. 커밋된 소스에서 검증한 정적 산출물을 별도 릴리스 디렉터리에 만든다. 운영에 작업 중인 `public/` 디렉터리를 그대로 연결하지 않는다.
2. 릴리스 저장소를 운영 컨테이너에 읽기 전용으로 마운트하고 Express가 제공하도록 하면 원본 `127.0.0.1:3000`과 기존 접근 경로를 유지하기 쉽다. nginx 직접 제공 방식도 가능하지만 공개·Tailscale·원본 경로 차이와 운영 설정 증가를 비교한다.
3. `/assets/<release>/css/...` 같은 버전 경로나 콘텐츠 해시 URL로 릴리스별 파일을 불변으로 보관한다. URL을 그대로 둔 채 immutable 파일을 덮어쓰면 안 된다. 예전 HTML이 요청하는 이전 버전도 정확한 이전 내용을 반환해야 한다.
4. 현재의 부팅 시점 `ASSET_VERSION`만으로는 무재시작 전환이 불가능하다. 런타임 매니페스트/에셋 URL helper 등을 통해 새 요청이 활성 릴리스를 참조하도록 한다. 매니페스트는 원자적으로 교체하고 읽기 실패 시 마지막 정상 버전을 유지한다. 한 응답 안에서 서로 다른 릴리스가 섞이지 않게 한다.
5. CSS 내부 `url()`·`@import`, 폰트·이미지 상대 경로, CSS/JS preload, 영어 경로, 에러 페이지, HTML/렌더 캐시까지 참조 경로를 조사한다. 모든 정적 파일에 일괄 immutable을 적용하지 않는다.
6. 앱 리비전과 에셋 리비전을 별도로 기록하고 호환 관계를 남긴다. 앱 배포·앱 롤백 때 해당 앱과 호환되는 에셋을 선택한다. EJS/JS 변경이 필요한 CSS를 CSS 전용 배포로 먼저 올리지 않는다.
7. 게시 스크립트(예: 신규 `scripts/deploy-assets`, 아직 없음)는 잠금 → staging 생성 → 표적 검증 → 원자적 활성화 → 상태 기록 순서로 구성한다. 앱 배포와 동시 실행되는 경우도 조정한다. 실패하면 현재 릴리스를 유지하고 이전 매니페스트로 즉시 롤백할 수 있어야 한다.
8. 이전 릴리스 보존·삭제 정책은 immutable TTL, 오래 열린 페이지, HTML 엣지 캐시를 고려한다. 최신 몇 개만 남기는 단순 삭제로 이전 URL을 깨뜨리지 않는다. 노출 디렉터리에는 공개 산출물만 포함하고 경로 탈출을 차단한다.

HTML 엣지 캐시 때문에 전환 직후 이전 버전이 보일 수 있다. 원본에서 검증하고 즉시 공개 반영이 필요할 때만 기존 `node scripts/cloudflare-purge.js <paths>`를 사용한다. CSS URL 버전 변경과 HTML 캐시 갱신은 별개의 문제다.

## 검증과 완료 기준

- CSS만 수정해 게시했을 때 Docker 빌드가 실행되지 않고 운영 컨테이너 ID·시작 시각이 유지된다.
- 새 HTML은 새 에셋을 참조하고, 이전/새 URL은 각각 정확한 불변 내용과 적절한 캐시 헤더를 반환한다.
- 생성 CSS 누락, 잘못된 매니페스트, 게시 중단, 동시 배포에도 현재 화면이 깨지지 않는다. 롤백이 재빌드·재시작 없이 가능하다.
- CSS 변경 검증은 관련 생성·정적 검사와 대표 화면의 브라우저 확인으로 제한한다. CSS 게시마다 무관한 DB·콘텐츠 전체 감사를 반복하지 않는다. 배포 구조 자체의 신규 실패/롤백 로직에는 의미 있는 자동 검증을 추가한다.
- 첫 구조 전환의 앱 배포는 기존 `scripts/deploy` 전체 검증을 따른다. 배포 후 브라우저는 대표 영향 화면에서 모바일/데스크톱·두 테마를 확인하고 언어별 참조가 깨지지 않는지 검사한다. 같은 검사를 개발/운영에서 불필요하게 중복하지 않는다.
- 문서만 수정한 커밋은 배포하지 않는다. 완료 후 운영 참고에 CSS 전용 게시·상태 확인·롤백 명령과 전체 배포가 필요한 조건을 기록한다.

## 이번 세션의 운영 상태와 주의점

인수인계 직전 운영 코드 리비전은 `aede226a34dade50735408c78841e983ad3f14ac`였다. 검색창 배경색 변경 커밋이다. 배포 중 중단 요청으로 스크립트는 종료 코드 143으로 끝났지만, 이미 주 컨테이너 교체가 진행된 상태였다. 전체 테스트·standby 검증은 통과했고, 이후 주 컨테이너 리비전 및 `/ready`의 `ok/db/redis: true`를 확인했다. 남은 동일 리비전 standby는 제거했다. 스크립트가 끝까지 정상 종료했다고 기록하면 안 된다.

다음 세션에서는 당시 상태를 현재 상태로 단정하지 말고 확인한다. 배포 중단 시 단계별 정리·복구와 잠금도 설계에 포함한다. 주 컨테이너를 임의 `docker run`으로 재생성하지 않는다.

사용자는 기존 `KimMinryoung/BichonWebpage` 저장소 푸시·운영 배포를 명시적으로 승인했다. 다만 주관적인 디자인 후보를 제안하는 단계에서 곧바로 운영에 적용하지 말아야 한다. 이미 사용자가 운영 화면을 보고 있으면 불필요한 별도 스크린샷을 반복해서 보여주지 않는다.

## 검색창 색상 관련 별도 미결 사항

- 다크 모드의 현재 `--search-bg: var(--clr-dark-raised)`는 사용자가 만족한다.
- 라이트 모드의 `color-mix(in srgb, var(--clr-ink) 10%, var(--clr-cream-light))`는 회색빛 베이지가 비활성 입력처럼 느껴져 불만족한다.
- 이번 요청은 대체 색상 추천이다. 라이트 색상을 임의로 변경하거나 배포하지 않는다. 밝은 하늘색·따뜻한 흰색 등이 후보이며 아직 선택되지 않았다.
- 토큰 원본은 `public/css/palette.css`. 입력과 검색 결과 개수 표시의 바탕이 같은 토큰을 사용하므로 함께 유지한다. 구현 때 [디자인 기준](design-system.md)을 따른다.

다음 세션 시작 요청 예: “`dev_docs/frontend-static-assets-deployment-handoff-20261005.md`를 읽고 CSS 변경을 Docker 재빌드·컨테이너 재시작 없이 검증·게시·롤백할 수 있도록 배포 구조를 개선해.”
