# CommuLingo 강좌 개선 인수인계 (2026-11-10)

2026-11-10 하루 동안 기존 강좌를 점검하고 두 강좌를 고친 기록과, 남은 후보·작업 방법이다. 형식 자체의 규칙은 [실습 형식 문서](commulingo-workshop-format.md), 데이터 쓰기 규칙은 `commulingo-data-ops` 스킬이 기준이다. 여기의 수치는 2026-11-10에 내보낸 강좌 문서에서 센 것이므로 작업 전에 다시 센다.

## 1. 소유자가 정한 기준

이날 받은 피드백이며 뒤 작업에도 그대로 적용한다.

- **문항 앞 설명은 있어야 한다.** 다 읽지 않더라도 설명 화면(`summary`·`learningFocus`·`conceptBrief`·`conceptMap`·`diagram`)을 둔다. 「도입이 길어 이탈한다」는 수치를 근거로 설명을 줄이거나 뒤로 옮기자고 제안하지 않는다. 형식을 바꿀 때도 기존 설명과 기존 문항의 요점을 버리지 않는다.
- **기준은 내용의 질과 학습 효율이다.** 정답이 가장 긴 보기인 비율 같은 보기 길이 편중은 개선의 중심 기준이 아니다(실습 형식의 검사가 요구하는 만큼만 맞추고, 글자 수를 채우려 군말을 넣지 않는다).
- **해설은 밀도 있게.** 「문제의 질은 좋지만 해설이 너무 길다」(평균 700자대)는 평을 받아 300자 안팎으로 다시 썼다. 반대로 100자대의 얇은 해설도 문제다.
- 문항은 설명 화면이나 그 문항의 지문·발췌문만으로 풀 수 있어야 한다(해설에만 근거가 있으면 안 된다).

## 4. 작업 방법 (전환 한 번의 순서)

「분기 2부」에서 쓴 방식이다. 작업물은 처음부터 `scripts/content/<작업>/`에 둔다(gitignore, R2 보관).

1. **내보내기**: `scripts/commulingo-data export scripts/content/<작업>/export course/<id>`. 편마다 `orig/chNN.json`(전환 전)과 `chapters/chNN.json`(작업본)으로 나누고, 편이 쓰는 사이트 문헌은 `scripts/commulingo-docs export <작업>/text <문헌 id …>`로 내보낸다.
2. **도구 복사**: `scripts/content/workshop-divergences-2-20261110/`의 `build.js`, `show.js`, `brief-view.js`, `reorder.js`, `show-doc.py`를 가져다 쓴다.
   - `node build.js [chNN]`: 쓰기 검사와 같은 규칙을 전환 전 강좌와 견주어 돌리고(모양, 내용 규칙, 문항 id 재사용, 사이트 문헌 앵커와 발췌 글자 일치) `course.json`을 만든다.
   - `node show.js chNN [en]`: 설명 화면과 문항을 학습자 순서로. `node brief-view.js chNN`: 문항만 짧게(검토용).
   - `node reorder.js chNN q1 q8 q2 …`: 문항 순서 바꾸기.
3. **지침**: 같은 폴더의 `BRIEF.md`(전환), `EXPL-BRIEF.md`(해설 다듬기), 1848 폴더의 `INTRO-BRIEF.md`(설명 화면 쓰기)를 그 강좌에 맞게 고쳐 쓴다. 핵심 규칙:
   - 설명 화면과 `readings`는 그대로 두고, 문항이 요구하는 사실이 없으면 `conceptBrief`에 보탠다.
   - 원래 여섯 요점은 모두 남긴다. 넷은 객관식(id 유지, 보기 3개 → 4개), 둘은 같은 요점의 활동(`qN-r<날짜>`), 새 활동 둘은 `q7`·`q8`.
   - 첫 문항은 객관식. 분류는 그 편에서 맞선 실제 쪽으로 가르고, 빈칸은 사이트 문헌 문장 그대로, 순서는 앞뒤 관계로 정해지는 것만.
   - 해설은 한국어 200~320자(상한 380자): 왜 그런가, 결정적 사실·인용, 어디로 이어졌거나 어디서 갈리는가.
4. **작성**: 편마다 하위 에이전트 하나(지침 파일과 맡은 편만 읽게 한다). 동시 실행 한도는 6개다.
5. **검토**: `brief-view.js`로 편마다 읽는다. 이날 검토에서 나온 유형: 문항 순서(배경 연표가 맨 끝에 놓임), 지어낸 낱말 풀이의 부정확(가치법칙), 직접 발언이 아닌 해석을 한쪽 주장으로 넣은 분류 항목, 보기 문체가 다른 편과 어긋남(한다체), 정답을 줄이며 빠진 내용(정답 피드백으로 옮겼는지 확인).
6. **반영**: `node build.js`로 `course.json`을 만들고 MCP `data_document_put`(`specPath: content/<작업>/course.json`, `expectedRevision`)을 dry run → 적용 → `stores_refresh`. 커밋·배포는 없다.
7. **확인**: 운영에서 한 편을 브라우저로 연다(`tests/lib/browser`의 `launchChromium`, 요청 헤더 `x-commulingo-test: 1`로 계측 제외, 주소에 `?verify=<시각>`). 화면은 `temp_dev/screenshots/`.
8. **문서**: [실습 형식 문서](commulingo-workshop-format.md)에 강좌별 절을 더한다.

## 5. 걸렸던 것

- **쓰기 검사는 배포된 코드로 돈다.** `scripts/lib/commulingo-checks.js`를 고쳐도 관리 MCP 컨테이너(`leninbot-frontend-mcp`)에 올리기 전에는 운영 dry run이 옛 규칙으로 거부한다. 작업 폴더의 `build.js`는 저장소 코드를 바로 쓰므로 둘의 결과가 다를 수 있다. 올리는 명령은 `scripts/deploy --mcp-only`.
- **배포 명령은 그때마다 허가를 받는다.** 이날 `scripts/deploy --mcp-only`가 권한 분류기에 막혔고 소유자의 명시적 허가 뒤에 실행했다. 전체 배포를 한 번 허가받았다고 다른 배포까지 허가된 것은 아니다.
- **실습 형식의 객관식은 4지선다 필수**다. 3지선다 강좌를 옮기면 편마다 오답과 `choiceFeedback`을 하나씩 더해야 한다. 더한 오답은 맞선 쪽의 실제 입장이나 흔한 오독으로 짠다.
- **합니다체 번역 문헌에는 발췌형 빈칸을 낼 수 없다**(`source-shape`: 발췌문 높임 어미). 그 문장은 객관식으로 두거나 `kind: 'reference'`로 낸다.
- **영어 빈칸 낱말은 30자 이하**라 `dictatorship of the proletariat`(31자) 같은 낱말은 표현을 바꾸거나 빈칸 범위를 줄여야 한다.
- **문항 물음과 정답을 함께 바꾸면 새 id가 필요하다.** 정답 보기를 뜻은 유지한 채 줄이는 것은 같은 id로 통과했다.
- `data_document_put` 결과의 `questionsChanged`는 물음·정답이 바뀐 문항만 세는 것으로 보인다(해설만 바꾼 쓰기는 0으로 나왔다). 해설 반영은 레슨 응답(`/commulingo/lesson/<id>`)으로 확인한다.
