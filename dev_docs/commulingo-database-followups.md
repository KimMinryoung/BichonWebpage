# CommuLingo DB 후속 개선 후보

작성일: 2026-09-07.
상태: **2026-09-30 전 항목 판정 완료.** 아래는 판정과 적용 결과다.

기존 구현과 복구 절차는 [저장 구조와 일관성](commulingo-database.md)을 참고한다. 아래는 해당 작업 이후 읽기 전용 점검에서 정리한 후속 후보이며, 확정된 구현 계획이 아니다.

| 후보 | 2026-09-30 판정 |
| --- | --- |
| 오래된 편집 화면의 덮어쓰기 방지 | **이미 해결.** 인물·절·용어 쓰기는 `expectedRevision`을 기본 필수로 검사한다(`requireRevision`을 끄는 곳은 테스트 fixture뿐). leninbot의 인물·절·용어 쓰기도 frontend 편집 서비스(RPC)를 거쳐 같은 검사를 받는다. |
| 마이그레이션 적용 이력 | **적용.** 마이그레이션 195 `schema_migrations`와 호스트 스크립트 `scripts/apply-migration`(postgres로 실행, 파일·sha256 기록, 같은 해시는 건너뜀, 적용 뒤 바뀐 파일은 `--force` 없이 거부, `--status`로 미기록·변경 파일 목록). 기존 203개 파일은 `--baseline`으로 "실행 없이 기록"했다. |
| 직책·재임 이력 편집 동시성 | **적용.** `people-offices-store.js`의 생성·수정·삭제가 직책 행을 먼저 `FOR UPDATE`로 잠그고(직책 → 직책 행 한 순서) 편집 대상을 잠금 아래에서 다시 읽는다. `scripts/test-commulingo-offices-db.js`(격리 DB)로 동시 생성 8건의 정렬값 중복 없음과 편집 16건 이력의 연쇄를 확인했다. |
| 답안 입력의 의미 검증 | **부분 적용.** 미래의 `lastAt`은 서버 현재 시각으로 자른다. 늦은 쪽이 이기는 병합이라 시계가 앞선 기기의 기록이 이후 답안을 영구히 막았기 때문이다. 카탈로그 존재 검사는 넣지 않았다: 영향이 자기 계정 행뿐이고, 폐기 id로 남은 오프라인 기록과의 호환을 깬다. |
| 외부 DB 수정의 캐시 반영 | **이미 해결.** 2차 리팩터 배치 9에서 사전 스냅숏이 저장소별 `pg_stat_user_tables` 쓰기 카운터 서명으로 갱신 여부를 판정하고(60주기, 약 1시간마다 전체 재조회), 외부 수정은 약 60초 안에 반영된다. NOTIFY는 불필요하다. |
| 로그인 사용자의 진도 저장 확인 | **코드 경로 이상 없음, 실사용 확인만 남음.** 일반 가입이 열려 있고 계정 11개가 있지만 `commulingo_progress`·`commulingo_question_progress`는 0행이다. 강좌 페이지는 캐시되지 않는 개인 응답이라 로그인 세션에 CSRF 토큰이 실리고, 저장 경로에도 이상이 없다. 로그인한 채 강좌를 푼 사람이 없었던 것으로 본다. 로그인 상태로 문항 하나를 풀고 두 표에 행이 생기는지 보면 확정된다. |
