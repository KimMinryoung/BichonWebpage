# CommuLingo DB 후속 개선 후보

작성일: 2026-09-07.
상태: **검토 후보만 기록. 사용자 지시에 따라 구현·DB 변경·배포는 진행하지 않는다.**

기존 구현과 복구 절차는 [저장 구조와 일관성](commulingo-database.md)을 참고한다. 아래는 해당 작업 이후 읽기 전용 점검에서 정리한 후속 후보이며, 확정된 구현 계획이 아니다.

| 우선순위 | 개선 후보 | 확인한 상태와 제안 |
| --- | --- | --- |
| 높음 | 오래된 편집 화면의 덮어쓰기 방지 | 기존 행 잠금은 동시에 실행되는 저장을 직렬화하지만, 오래전에 읽은 내용을 나중에 제출하는 편집까지 감지하지 않는다. 편집 버전을 요청에 포함하고 현재 버전과 다르면 충돌로 처리하는 방식을 검토한다. |
| 높음 | 마이그레이션 적용 이력 | 현재 scripts/apply-migration.js는 SQL 파일을 실행하며, public 스키마에서 이름에 migration이 포함된 이력 테이블은 발견되지 않았다. 적용 번호·파일 해시·적용 시각을 기록하고 중복 실행 및 적용 후 파일 변경을 감지하는 방식을 검토한다. |
| 중간 | 직책·재임 이력 편집 동시성 | people-offices-store.js의 직책 이력 저장·수정·삭제는 기존 상태를 명시적 행 잠금 없이 읽는다. 같은 직책의 동시 편집으로 이력의 전후 상태가 섞이지 않도록 잠금 범위와 순서를 검토한다. |
| 중간 | 답안 입력의 의미 검증 | 수업 ID는 길이, 문제 ID는 q숫자 형식 위주로 검사한다. 파일 카탈로그에 실제 수업·문제가 존재하는지 확인하는 검증과 지나치게 미래인 lastAt 처리 정책을 검토한다. 오프라인 답안과 기존 ID 호환성도 고려해야 한다. |
| 중간 | 외부 DB 수정의 캐시 반영 | Admin 외부 수정은 주기 갱신에 의존한다. DB 알림으로 갱신을 유도하고 재연결 시 영속 변경 버전을 확인하는 방식을 검토한다. 알림만을 유일한 변경 감지 수단으로 삼지 않는다. |

PostgreSQL NOTIFY는 트랜잭션 커밋 후 알림을 전달한다. 참고: [PostgreSQL 17 NOTIFY 문서](https://www.postgresql.org/docs/17/sql-notify.html).

## 먼저 확인할 운영 현황

점검 당시 commulingo_progress와 commulingo_question_progress는 정확한 COUNT 조회에서 각각 0행이었다. 비로그인 사용자의 localStorage 이용만 있었다면 정상일 수 있으므로, 이것만으로 저장 장애라고 단정하지 않는다. 실제 로그인 학습 이력이 있다면 해당 계정의 저장 요청·인증·CSRF·응답 경로부터 확인할 필요가 있다.

앞선 양방향 동기화 브라우저 검증은 독립 테스트 DB와 테스트 계정 환경에서 수행했다. 운영 실사용 계정의 저장 성공을 확인한 것은 아니다.

## 제안한 검토 순서

1. 실제 로그인 계정의 진도 저장 여부 확인.
2. 편집 버전 검사 도입 검토.
3. 마이그레이션 적용 이력 관리 검토.
4. 직책 이력 잠금, 답안 의미 검증, 외부 수정 캐시 갱신 검토.

수치와 코드 상태는 후속 작업을 명시적으로 요청받았을 때 다시 확인한다.
